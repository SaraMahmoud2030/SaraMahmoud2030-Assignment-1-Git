1. git squash

يُستخدم لدمج أكثر من commit في commit واحدة، بحيث يصبح تاريخ المشروع أكثر ترتيبًا وأقل ازدحام

لو عملت Feature وعملت أثناء تنفيذها عدة commits صغيرة مثل إصلاح خطأ وتعديل بسيط وتحسين للكود، أقدر أعمل squash وأجمعهم في commit واحدة قبل دمج الـfeature في "main".
===================

2. git merge vs git rebase

git merge

يُستخدم لدمج التغييرات الموجودة في branch مع branch آخر، مع الحفاظ على تاريخ الـcommits كما هو، وقد ينتج عنه merge commit.

Real-world Scenario:
لو أنا شغالة على "feature/login" وخلصت الـfeature وعايزة أضمها إلى "main"، أقدر أستخدم "git merge".

git rebase

يُعيد ترتيب الـcommits الخاصة بالـbranch بحيث تبدأ من أحدث نقطة في الـbranch الأساسي، مما يجعل تاريخ الـcommits أكثر خطية.

Real-world Scenario:
لو أنا شغالة على feature والـ"main" اتقدم بcommits جديدة، ممكن أعمل rebase على "main" قبل ما أرفع الـfeature، بحيث أشتغل على أحدث نسخة من المشروع.

3. git help

يُستخدم للحصول على المساعدة والمعلومات عن أوامر Git وطريقة استخدامها.


لو نسيت طريقة استخدام command معينة مثل "git rebase"، أقدر أستخدم:

git help rebase

لمعرفة تفاصيل استخدامها.

===============================
4. git cherry-pick

يُستخدم لتطبيق commit معينة من branch على branch آخر، بدون دمج الـbranch بالكامل.

لو زميلي عمل commit فيها إصلاح لخطأ مهم، وأنا محتاجة الإصلاح ده فقط في الـbranch بتاعي، أقدر أستخدم "git cherry-pick" للـcommit المطلوبة بدل ما أضم كل تغييرات الـbranch.

---

5. git clean

يُستخدم لحذف الملفات غير المتتبعة بواسطة Git (untracked files) من الـworking 

لو عندي ملفات مؤقتة أو ملفات generated اتعملت أثناء تشغيل المشروع ومش محتاجها ومش عايز أضيفها للـrepository، أقدر أستخدم "git clean" لتنظيف الـworking directory.

---

6. git grep


يُستخدم للبحث عن كلمة أو نص داخل الملفات التي يتتبعها Git.

لو المشروع كبير وعايز أعرف كل الأماكن التي يتم فيها استخدام اسم class أو function معينة، أقدر أبحث عنها باستخدام "git grep".

---

7. git blame

يُستخدم لمعرفة الـcommit والـauthor المرتبطين بكل سطر من أسطر ملف معين.

لو لقيت سطر في المشروع فيه مشكلة وعايز أعرف مين عدله ومتى، أقدر أستخدم "git blame" لمعرفة تاريخ هذا السطر والـcommit المرتبطة به.

---

8. git bisect

يُستخدم للبحث عن الـcommit التي أدخلت Bug عن طريق تقسيم تاريخ الـcommits إلى أجزاء واختبارها تدريجيًا.

لو المشروع كان شغال بشكل صحيح ثم ظهر Bug، ومش عارف ظهر في أي commit، أقدر أستخدم "git bisect" لتحديد الـcommit التي سببت المشكلة بدل ما أراجع كل الـcommits يدويًا.

==========

9. git shortlog

يُستخدم لعرض ملخص للـcommits، ويمكن استخدامه لمعرفة عدد الـcommits التي قام بها كل contributor.

في مشروع فيه أكثر من developer، أقدر أستخدم "git shortlog" للحصول على ملخص للـcommits ومعرفة مساهمات كل developer.

---

10. git prune

يُستخدم لحذف Git objects غير القابلة للوصول من الـrepository بعد أن تصبح غير مستخدمة.

بعد عمليات كثيرة مثل حذف branches أو إعادة كتابة التاريخ، قد تبقى objects قديمة غير مستخدمة. يمكن استخدام "git prune" لتنظيف هذه الـobjects.

======

11. git worktree

يسمح بإنشاء أكثر من working directory لنفس الـGit repository، بحيث يمكن العمل على أكثر من branch في نفس الوقت.

لو أنا شغالة على feature معينة، وفجأة محتاجة أشتغل على Bug عاجل في branch آخر، أقدر أستخدم "git worktree" لإنشاء working directory ثانية للـbranch الآخر بدون ما أضطر أعمل stash لتغييراتي الحالية.

---

12. git verify-commit

يُستخدم للتحقق من صحة التوقيع الرقمي الموجود على commit، إذا كانت الـcommit موقعة.

في مشروع مهم، ممكن الفريق يشترط أن تكون الـcommits موقعة رقميًا للتأكد من أن الـcommit تم إنشاؤها من الشخص صاحب المفتاح المستخدم للتوقيع. أقدر أستخدم "git verify-commit" للتحقق من التوقيع.

==============

13. git filter-repo

أداة تُستخدم لإعادة كتابة تاريخ Git repository، مثل إزالة ملفات أو بيانات حساسة من الـhistory.

لو developer رفع ملف يحتوي على معلومات  سرية إلى repository ثم حذف الملف في commit لاحقة، فإن المعلومات قد تظل موجودة في تاريخ Git. يمكن استخدام "git filter-repo" لإعادة كتابة التاريخ وإزالة هذه البيانات من الـhistory.
=============
